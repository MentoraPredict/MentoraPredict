# ADR 0003 — Messaging Strategy: Drop RabbitMQ, Direct HTTP + Socket.IO

Status: Accepted

Context
- RabbitMQ was wired into `auth-service`, `academic-service`, `analytics-service` and `prediction-service` as an event bus (`student.login`, `grade.recorded`), but none of the `ClientsModule` registrations set an `exchange`, so every producer's `emit()` published to its *own* queue (`sendToQueue` under the hood) instead of the queue any consumer was actually listening on. In practice no message published by this stack ever reached a remote `@EventPattern` handler, and the two consumers that did exist (`grade-event.consumer.ts` in analytics-service and prediction-service) were no-op stubs (log + ack, no side effect).
- The one real-time-ish feature that exists — user notifications (`notifications` table, owned by analytics-service) — never went through RabbitMQ at all. It's created synchronously in-process inside `RecalculateStudentMetricsUseCase`, triggered by a direct HTTP call. The frontend only fetched notifications once on mount, with no push mechanism.
- The RabbitMQ container itself was capped at 0.30 CPU / 384M memory (tight for the management-plugin image) and had a documented history of slow/flaky local startup.
- The project needs two things going forward: (1) a way for one service to tell another "this happened" (e.g. academic-service telling analytics-service to create a notification when a student is enrolled or a course is created), and (2) real-time delivery of that notification to an open browser tab, which nothing in the stack provided.

Decision
- Remove RabbitMQ entirely: the broker, `@nestjs/microservices`/`amqplib`/`amqp-connection-manager` dependencies, the `packages/event-contracts` package, and all `RABBITMQ_*` env vars/compose services/CI steps.
- Service-to-service signaling uses direct internal HTTP calls (fire-and-forget, same `InternalJwtService` + `InternalServiceGuard` pattern already used for `IAnalyticsClientPort.triggerRecalculate` and `UserProfileHttpClient`), not a broker. This is simpler to operate, and failures are visible (a non-2xx response gets logged) instead of silently vanishing into a misconfigured queue.
- Real-time delivery to the browser uses Socket.IO, hosted by `analytics-service` (the existing owner of the `notifications` domain) at `/api/socket.io`, authenticated via the same RS256 JWT already used everywhere else (verified on the socket handshake, not via Kong's `jwt` plugin — the Socket.IO handshake doesn't carry the token as a standard `Authorization` header). One room per user (`user:{userId}`) keeps fan-out trivial. If nobody is connected, the notification still persists in Postgres and is picked up on next `GET /api/v1/notifications/me`.
- `NotificationEntity` was generalized: `recipientRole` now includes `ADMIN`, `type` now includes `ENROLLMENT_CREATED`/`COURSE_CREATED` alongside the original `RISK_ESCALATION`, and the risk-specific fields (`relatedAlertId`, `subjectId`, `studentId`, `periodId`) became nullable so non-risk notifications don't need to fake them. A new generic `CreateNotificationUseCase` + `POST /api/v1/notifications/internal` accepts either a specific `recipientId` or a `broadcastToRole` (resolved via a new `GET /api/v1/users/internal/by-role` on user-service), so any service can trigger a notification — targeted or role-wide — without analytics-service needing to know who's calling.

Consequences
- One fewer piece of infrastructure to run and monitor locally and in CI (no RabbitMQ container, no queue health checks).
- Service-to-service notification triggers are fire-and-forget HTTP calls: if analytics-service is briefly unreachable, the triggering action (enroll a student, create a course) still succeeds, but the notification is silently dropped for that one call — same trade-off the project already accepted for `triggerRecalculate`. There is no retry/outbox; if this becomes a real problem, revisit before reintroducing a broker.
- Socket.IO requires `nginx` to forward `Upgrade`/`Connection` headers correctly (`apps/web/nginx.conf` now uses a `map $http_upgrade $connection_upgrade` block instead of unconditionally clearing `Connection`) and a dedicated Kong route (`/api/socket.io`, no `jwt` plugin — auth happens inside `NotificationsGateway` instead).
- `RegisterGradeUseCase` (registering an individual grade) now calls `IAnalyticsClientPort.triggerRecalculate` directly instead of emitting a `grade.recorded` event that nothing consumed — this was effectively a bug fix that fell out of the RabbitMQ removal, not a separate change.
- Extending notifications further (e.g. "grade imported", "check-in overdue") means: call `INotificationClientPort.notify(...)` (academic-service) or the equivalent internal HTTP client from any other service, with a `recipientId`+`recipientRole` or a `broadcastToRole`. No new infrastructure is needed.

Notes
- If the app ever needs multiple `analytics-service` replicas, `NotificationsGateway` needs a Socket.IO Redis adapter (`@socket.io/redis-adapter`) so rooms are shared across instances — Redis is already deployed for caching, so this is a config change, not new infrastructure.
